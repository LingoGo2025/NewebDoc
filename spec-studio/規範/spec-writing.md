# 開發說明、SA 規格與 API 規格寫法（通用）

規格各頁段落的順序：頁面說明 → 「對應流程」→ 開發說明（AI 補充）→ 開發說明（設計者補充）→ SA 規格 → `**畫面文字（依 SVG 順序）**`。這些區塊都由 `dev_notes.py` 打包成 `assets/dev_notes.js`，改完任何一段都要執行 `python3 scripts/dev_notes.py`。

## 開發說明

- 各頁於規格「對應流程」後有兩段：「開發說明（AI 補充）」（AI 依現有規格撰寫，不補未知規格）與「開發說明（設計者補充）」（設計者要求補充才寫，沒有就留空）。
- 燈箱第三個頁籤上下兩區都固定保留，設計者區沒有內容也不隱藏。

寫法：

```markdown
- 開發說明（AI 補充）：
  - 項目
- 開發說明（設計者補充）：
```

## 說明對照（燈箱「說明」按鈕）

示意圖工具列的「說明」按鈕會把開發說明標在畫面對應的區塊上（半透明底色＋虛線框＋編號標籤），全文列在右側「開發說明對照」，兩邊滑過互相標亮；沒有對應區塊的說明列為「整頁說明」。

- 對應方式：開發說明（AI 補充）每條以 `【標籤】` 開頭；頁面 SVG 中對應的區塊加上同名記號 `data-note="標籤"`（可加在區塊的 `<g>`，或在區塊位置放一個看不見的 `<rect data-note="標籤" x y width height fill="none" stroke="none"/>`）。記號跟著區塊走，區塊標題改字、搬位置都不會失效。
- 適合對應的是講某一塊畫面的說明（欄位、清單、按鈕列、提示區）；【頁面目的】【進入方式】【待確認】這類整頁性質的說明不加記號。不確定對到哪一塊時寧可不加，不要猜。
- `mockup.py` 的區塊可寫 `devnote`（輸出為 `data-note`）；全自動起稿會把【主要欄位】【操作】自動對到表單／表格與按鈕列。
- 標籤改名時同步改 SVG 記號；`check.py` 會提醒「SVG 有記號但開發說明沒有同名標籤」與重複記號。刪除或拆開區塊後，`dev_notes.py` 會提醒哪條說明失去對應（燈箱自動改列為整頁說明），依需要在新的區塊補上記號。
- 一個標籤只對一個區塊；一頁內記號不可重複。

## 開發說明維護（每次必做）

新增、刪除、更名或調整頁面功能、欄位、狀態、文案、跨頁關聯、待確認事項時，須依**最後定案的設計**（Markdown 規格與 SVG 一致後）重寫或修正受影響頁面的「開發說明（AI 補充）」，不可沿用已過時的說明。

- 新增頁面須同步補上兩段（AI 補充＋空的設計者補充）；刪除頁面一併刪除。
- AI 補充只整理已定案內容與標示「待確認」的未知事項，不自行補成既定規格；與頁面說明、流程、「尚待確認事項」衝突時以規格為準並一併修正。
- 「開發說明（設計者補充）」只在設計者明確要求時才寫入，AI 不自行填寫、不得刪改設計者已寫的內容，沒有就留空。
- 改完執行 `python3 scripts/dev_notes.py`，並在更新紀錄寫明已更新的頁面。

## SA 規格

- 每頁都有，放在「開發說明（設計者補充）」之後、`**畫面文字（依 SVG 順序）**` 之前，小節用 `####`，內容只用 Markdown 表格與條列（不可用 `<a id>` 或 `##`／`###` 標題，否則會切斷段落解析）。
- 燈箱第四個頁籤「SA 規格」顯示，並把「待確認」標為橘色。
- 三種標記：
  - `**SA 規格（待補）**`：空白骨架（引言＋11 個固定小節標題、無內容），等功能確認後再補，不自行先填。燈箱對空白小節顯示「待補」。全自動起稿時，只在「摘要｜本頁待確認」列出待確認事項，其他小節維持空白。
  - `**SA 規格（試做）**`：試寫中的頁面（目前有哪些頁見 `專案規則.md` 或 `inventory.py` 輸出）。
  - `**SA 規格**`：已補完並經使用者確認。補內容時依下方「SA 各小節寫法」與「依示意圖與流程補 SA」填寫。
- 新增頁面時一併放入空白骨架（可從任一待補頁複製）；`check.py` 會提醒缺少 SA 規格區塊的頁面。
- 兩層寫法：小節標題以 `摘要｜` 開頭者給人審閱（頁面目的與入口、關鍵規則、已定案、本頁待確認，控制在一個畫面內），以 `明細｜` 開頭者給開發使用（欄位、導向、狀態、本頁錯誤文案、資料寫入、驗收條件），燈箱預設收合。
- 全站共用規則：規格章節「## 全站共用規則（試做）」（錨點 `common-rules`）集中寫共用欄位規則 CF、表單行為 CB、畫面狀態、錯誤文案 CE、驗收條件 CAC 與非功能需求；各頁只寫特有內容並以編號引用，不重複抄寫。「（預設規則）」在共用章節確認一次即全站適用。燈箱在 SA 規格頁籤底部以收合區塊顯示共用規則。
- 已改用兩層寫法的頁面，「開發說明（AI 補充）」只保留頁面目的與指向 SA 規格的說明，避免三層重複；尚未改的頁面維持原寫法。


### SA 各小節寫法（格式固定）

每頁 11 個小節，順序與標題固定（`page_stub.py` 產生的骨架）。表格欄位照下表，不自行增減欄位；沒有內容的小節寫一行說明（例如「本頁不寫入資料」），不要留空。

| 小節 | 格式 | 寫什麼 | 主要來源 |
|---|---|---|---|
| 摘要｜頁面目的與入口 | 條列 2–4 行 | 頁面目的一句；誰使用；從哪裡進入（網站地圖節點、流程的上一步頁面、其他頁的按鈕） | 頁面說明、網站地圖、流程 `@order` |
| 摘要｜關鍵規則 | 表 `編號｜規則` | 一條一個可驗證的業務規則：顯示條件、互斥、限制、計算、權限；引用欄位編號 F、其他頁 ID、共用規則編號 | 示意圖的提示文字與狀態、流程分支、業務規則 |
| 摘要｜已定案 | 條列 `- YYYY-MM-DD：內容` | 使用者確認過的決定；沒有寫「尚無」 | 使用者確認紀錄 |
| 摘要｜本頁待確認 | 表 `編號｜問題｜影響` | 本頁還不能定的事；影響欄寫受影響的頁面 ID | 起稿的待確認、補寫時發現的缺口 |
| 明細｜基本資訊 | 表 `項目｜內容` | 固定列：進入方式、網址格式、使用者與權限、前置條件、後置條件、頁面區塊（依 SVG 由上而下）、資料來源 | 網站地圖、流程、示意圖版面 |
| 明細｜欄位規格 | 表 `編號｜欄位｜元件｜必填｜預設值｜規則｜錯誤` | 示意圖上每個輸入欄位一列，依 SVG 由上而下；元件寫輸入、下拉、日期、多行、上傳、單選、複選、唯讀顯示；規則引用 CF 或寫本頁規則；錯誤引用 CE 或本頁 E 碼。列表頁另以條列寫「列表欄位：…（排序、分頁依 CB）」；系統帶入與唯讀顯示的資料用條列補充 | 示意圖的表單、查詢列、表格欄位 |
| 明細｜按鈕與導向 | 表 `元件｜條件｜動作` | 示意圖上每個按鈕、連結、頁籤、每列操作都要列；動作寫導向頁面 ID、開啟的視窗或後端動作；共用選單可用一行引用共用選單表 | 示意圖的按鈕與連結、流程的下一步 |
| 明細｜畫面狀態 | 表 `狀態｜條件｜呈現` | 本頁特有狀態（例如不同身分、資料狀態造成的差異、狀態標籤的每種值）；載入、空資料、送出中、系統錯誤等共用狀態用一行引用共用規則 | 示意圖的狀態標籤與頁籤、流程分支 |
| 明細｜本頁錯誤文案 | 表 `代碼｜觸發｜文案` | 本頁特有錯誤；共用錯誤引用 CE 不重寫；文案未定時小節標題加「（建議文案，待確認）」 | 欄位規則、流程的失敗分支 |
| 明細｜資料寫入 | 表 `情境｜寫入資料｜初始狀態` | 送出或操作後新增、更新的資料與狀態；唯讀頁寫「本頁不寫入資料」，查詢頁可寫「讀取：…」 | 流程中寫入服務或資料庫的步驟 |
| 明細｜驗收條件 | 表 `編號｜前提｜操作｜預期結果` | 每條關鍵規則、每個本頁錯誤、每條相關流程的成功與失敗分支至少各一條；最後一行寫「另須通過共用驗收條件 CAC-…」 | 關鍵規則、錯誤文案、流程 |

### 編號規則

| 種類 | 格式 | 範圍 |
|---|---|---|
| 關鍵規則 | `BR-<頁面ID>-01` | 每頁從 01 起 |
| 欄位 | `F01` | 每頁從 01 起，依 SVG 由上而下 |
| 本頁錯誤 | `E01` | 每頁從 01 起 |
| 本頁待確認 | `Q01` | 每頁從 01 起 |
| 驗收條件 | `AC01` | 每頁從 01 起 |
| 共用規則 | `CF-01`、`CB-01`、`CE-01`、`CAC-01` | 全站，寫在「全站共用規則」章 |

- 「（預設規則）」：AI 依常見做法先訂、等使用者確認的規則；「（待確認）」：不能推測、要問人的事，同時列入「本頁待確認」。
- 不可推測：API 欄位與加解密、金流細節、法規條文、商業政策、費率、金額與期限，一律寫「待確認」。

### 依示意圖與流程補 SA（第 11 階段）

版面與流程審閱完、使用者要求「依示意圖與流程產出 SA」時，照下列步驟逐頁補：

1. **取得素材**：`python3 scripts/sa_context.py <頁面ID>`，一次列出該頁的頁面說明、畫面文字（依 SVG 順序）、示意圖上的欄位與按鈕、相關流程的步驟與上下游頁面、網站地圖的類似與管理關聯、本頁待確認、全站共用規則編號。
2. **對照寫入**：

   | 素材 | 寫進 |
   |---|---|
   | 示意圖的輸入欄位、查詢條件 | 明細｜欄位規格（F 編號依 SVG 順序） |
   | 示意圖的表格欄位 | 明細｜欄位規格的「列表欄位」條列 |
   | 示意圖的按鈕、連結、頁籤、每列操作 | 明細｜按鈕與導向 |
   | 示意圖的狀態標籤、提示框、頁籤數量 | 明細｜畫面狀態、摘要｜關鍵規則 |
   | 流程的上一步、下一步頁面 | 摘要｜頁面目的與入口、明細｜基本資訊（前置、後置條件）、按鈕與導向 |
   | 流程中寫入服務或資料庫的步驟 | 明細｜資料寫入 |
   | 流程的 `alt` 成功與失敗分支 | 本頁錯誤文案、驗收條件 |
   | 網站地圖的「管理」頁面 | 明細｜基本資訊的資料來源 |
   | 本頁待確認、規格「尚待確認」 | 摘要｜本頁待確認 |
   | 全站共用規則 | 只引用編號，不重寫 |

3. **示意圖與流程不一致時**（例如流程有的按鈕示意圖上沒有），列入「本頁待確認」並告訴使用者，不要自行改圖。
4. **標記**：寫完把 `**SA 規格（待補）**` 改為 `**SA 規格（試做）**`；使用者確認後改為 `**SA 規格**`，並在「摘要｜已定案」記錄日期。該頁「開發說明（AI 補充）」縮成頁面目的與「見 SA 規格」。
5. **檢查**：執行 `python3 scripts/dev_notes.py`、`python3 scripts/inventory.py`、`python3 scripts/check.py`（會提醒 SA 小節空白、編號不連續、欄位沒有對應的驗收條件等）。
6. **批次**：一次一個模組或一個區域（約 3–6 頁），每頁回報關鍵規則、欄位、驗收條件的數量與新增的待確認事項，再進下一批。

### SA 自查清單

- 示意圖上每個輸入欄位都在欄位規格；每個按鈕、連結都在按鈕與導向。
- 每條關鍵規則至少一條驗收條件；每個本頁錯誤 E 碼都被欄位規格或驗收條件引用。
- 相關流程的成功與失敗分支都有驗收條件。
- 共用規則只引用編號，沒有重抄。
- 不能推測的內容都寫「待確認」並列入本頁待確認。

## API 規格

- 網站地圖 API 區一個按鈕＝一支 API＝一個網址（Notify／Return 等回傳屬同一支 API）。
- 規格「## API 介接」章每支 API（`### API01｜…`）有「開發說明」兩段，以及 `**API 規格（…）**` 區塊（`####` 小節：介接資訊、傳送欄位、回傳欄位｜<回傳對象>、加解密方式；寫法同 SA 規格）。
- 「- 對應頁面：」列出該 API 開啟或關聯的頁面。`dev_notes.py` 打包為該 API 的 `api`、`pages`，改完一樣執行。
- 傳送欄位表：欄位｜英文欄位名稱｜必填｜型態｜欄位大小｜說明；回傳欄位表：欄位｜英文欄位名稱｜型態｜欄位大小｜說明。
- 欄位與演算法未定者一律標待確認，不沿用舊版技術手冊內容；`check.py` 檢查每支 API 的區塊與小節。
