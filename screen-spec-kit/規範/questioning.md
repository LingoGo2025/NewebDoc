# 提問規則（通用）

AI 向使用者提問時依本檔進行。適用於修改既有專案（`修改專案.md`）與新專案訪談（`新專案.md`）。

## 1. 通用原則

1. **先查再問**：提問前先用 `section.py`、`impact.py` 查規格、網站地圖與 `專案規則.md`；文件已有答案的不問，只在回報時引用（「規格 A05 已寫明…」）。
2. **一次一個主題，最多 3–4 題**：同一輪的問題屬於同一主題；問完、寫入、確認後再進下一個主題。
3. **選擇題優先**：
   - 有提問工具（如 AskUserQuestion）時用它；沒有時用文字列出編號選項，請使用者回覆編號。
   - 每題 2–4 個選項，第一個是建議答案，標「（建議）」並用一句話說明原因。
   - 一定保留讓使用者自填的方式（工具內建「其他」，或文字註明「也可以直接描述」）。
   - 只有答案無法列舉時（名稱、文案、數值）才用開放題，並附一個範例答案。
4. **每題說明影響**：題目或選項說明中寫出答案會影響哪些頁面、流程或規則，例如「會決定 A05、B28 與捐款小物流程是否一起改」。
5. **答不出來不卡住**：使用者回答「不知道」「之後再說」或略過時，標「待確認」、加入規格「尚待確認事項」，繼續下一題；不追問、不替使用者決定。
6. **敏感領域不給建議答案**：API 欄位與演算法、金流、法規、商業政策（價格、費用、合約條件）只列出需要決定的事項，不標「（建議）」、不預設選項；使用者沒有明確回答就標待確認。
7. **每輪結束回放摘要**：把這一輪的答案整理成「將寫入的文字＋位置」（檔案、章節或頁面 ID），使用者確認後才寫入；使用者修正時改摘要再確認一次。
8. **不重複問**：已回答或已標待確認的事項，同一次對話不再問；需要推翻先前答案時，引用原答案並說明為什麼要重問。
9. **問題本身要能獨立看懂**：使用者可能只看到提問視窗，題目要寫出對象（頁面 ID 與名稱、流程名稱），不寫「上面提到的那頁」。

## 2. 修改既有專案的四種問題

| 類型 | 何時問 | 例子 | 備註 |
|---|---|---|---|
| 範圍確認 | 每次改檔前（標準流程第 2 步），必問 | 「確定改 A05、B28；A18 小物捐款頁是否一起改？」 | 列出「確定要改」與「待確認」兩組；使用者同意前不改檔 |
| 需求釐清 | 需求有兩種以上合理解讀 | 「『加一個欄位』是加在 A04 捐款頁，還是 B28 小物設定頁？」 | 選項就是各種解讀，第一個是最符合現有規格的解讀 |
| 規則衝突 | 新需求違反 `專案規則.md` 或共用規範 | 「這會讓小物出現『售價』，違反捐款小物規則。要調整需求，還是修改規則？」 | 先引用被違反的規則原文；改規則時連帶更新 `AGENTS.md`／`project.json` |
| 待確認定案 | 修改範圍碰到既有的「待確認」項目 | 「A03 政治獻金檢核條件目前待確認，這次要定案，還是維持待確認？」 | 「維持待確認」一定是選項之一；敏感領域依原則 6 |

順序：一次修改需要多種問題時，依「需求釐清 → 規則衝突 → 待確認定案 → 範圍確認」問，範圍確認放最後，因為範圍取決於前面的答案。

## 3. 新專案訪談階段（供 `新專案.md` 使用）

新專案依 `新專案.md` 進行（問完主題後讓使用者選「階段式」或「全自動」。全自動由 AI 一輪最多問 10 題、每題附 AI 建議，之後直接產生 12 個階段的第一輪資料，各階段改為「審閱起稿」，問法變成請使用者對初稿逐項回答保留、修改或刪除；下表的「問什麼」就是審閱時要確認的內容）：先以 `tools/init_project.py` 建立空白專案（範本已在各階段要填的位置放「〔待訪談第 n 階段〕」標記），再依下表逐階段填入、移除標記；`scripts/interview_status.py` 列出各階段狀態，中斷後從下一個未完成的階段接續。各階段的寫法見 `stages.md`。

依序進行，每階段套用第 1 節原則；第 1–10 階段建立整體架構，第 11 階段可逐頁分次進行。「網頁呈現」欄是該階段的答案最後出現在 index.html 的位置（首頁折疊區塊與燈箱，見 `index-page.md`）。

| 階段 | 問什麼 | 寫到 | 完成條件 | 網頁呈現 |
|---|---|---|---|---|
| 1 專案概要 | 平台目的、品牌名稱與標誌、品牌主色（可給色碼或描述）、上線範圍、回答語言 | 規格開頭、`專案規則.md`、`project.json › name`、`brand`、`theme` | 一段專案說明經使用者確認 | 頁首品牌標誌 |
| 2 使用者與角色 | 誰會使用、各角色能做什麼、是否有後台管理者 | 規格「系統架構 › 使用者」表 | 每個角色有名稱與一句說明 | 「系統架構」區塊的系統情境圖 |
| 3 業務規則與用語限制 | 本案特有的業務規則（例如某類物品是非賣品、某些身分不能使用某功能）、畫面不得出現的用語與允許的否定寫法 | `專案規則.md`「業務規則與用語限制」、`project.json › term_rules`、受影響頁面的規格 | 每條規則有一句說明；用語限制列出禁用詞與允許的否定寫法，或明確表示沒有 | 不直接顯示；`check.py` 用語檢查會擋下違規畫面 |
| 4 區域 | 網站分哪幾區（前台、會員中心、後台、API…）、各區 ID 字首 | `project.json › regions`、`ids`、`mockup`（各區版型：後台側欄或前台頂部導覽）；網站地圖「全站區域」表 | 每區有名稱、對象、ID 字首 | 「網站地圖」區塊的區域欄 |
| 5 頁面清單 | 每區有哪些功能節點、各節點有哪些頁 | 網站地圖節點與按鈕、規格各頁標題 | 每頁有 ID、名稱、所屬節點；共用選單項目確定 | 「網站地圖」區塊的頁面按鈕 |
| 6 業務模組 | 頁面依業務分成哪幾個模組、有哪些共用服務（通知、檔案、稽核等）、哪些頁面暫不歸入模組 | 規格「系統架構 › 業務模組」「共用服務」表、`architecture/` 功能架構圖 | 每頁歸入一個模組或列在「暫不歸入模組」，每個模組有名稱與一句說明 | 「系統架構」區塊的功能架構圖 |
| 7 跨頁流程 | 主要任務從哪頁開始、經過哪些頁、在哪結束 | `flows/*.puml`（`@pages`、`@order`、`@summary`）、規格流程段落 | 每條主要任務有頁面順序與摘要 | 燈箱「流程位置」、流程圖 |
| 8 外部系統 | 我方要串接的金流、物流、簡訊／郵件、身分驗證、測試與文件系統等 | 規格「系統架構 › 外部系統」表（含需求類別） | 每個系統有用途、需求類別、介接狀態（可為待確認） | 「外部系統串接」區塊 |
| 9 對外 API | 有 API 區時才問：平台對外提供哪些 API（一支 API 一個網址）、誰呼叫、開啟或關聯哪些頁面、呼叫流程；欄位與加解密依原則 6 不給建議 | 網站地圖 API 區按鈕、規格「API 介接」章各 API（介接資訊、傳送欄位、回傳欄位、加解密方式，見 `spec-writing.md`）、API 流程圖 | 每支 API 有 ID、名稱、對應頁面與流程，欄位未定者標待確認 | 網站地圖 API 區、燈箱 API 模式頁籤 |
| 10 全站共用規則 | 共用欄位格式（姓名、電話、Email 等）、表單行為、畫面狀態、錯誤文案、驗收條件、非功能需求 | 規格「全站共用規則」章（CF、CB、CE、CAC 編號，見 `spec-writing.md`） | 每類有一組預設規則經使用者確認，或標待確認 | 燈箱 SA 規格頁籤底部的共用規則 |
| 11 逐頁細節 | 欄位、狀態、按鈕、主要文案、錯誤情境（共用的部分引用第 10 階段編號） | 規格各頁段落、SVG、開發說明、SA 規格 | 該頁規格與 SVG 一致，未知處標待確認 | 燈箱的頁面示意圖、頁面說明、開發說明、SA 規格 |
| 12 選填 | 舊系統移轉、相關法規 | 選填章節 | 使用者提供內容，或明確表示略過 | 「舊系統移轉計畫」「相關法規」區塊 |

- 每完成一個階段，回報這階段的摘要與累計的待確認數量，並問要繼續下一階段還是先停。
- 使用者想跳階段時可以跳，但第 4、5 階段（區域與頁面清單）完成前不畫 SVG、不建流程，因為頁面 ID 尚未確定；第 6 階段要等頁面清單確定才能歸模組。
- 第 8 階段是我方去串接的外部系統，第 9 階段是我方提供給別人的 API，方向相反，不要合併提問。
- 第 10 階段放在逐頁細節之前，讓各頁只寫特有內容、以編號引用共用規則，不必每頁重問。
- 第 3 階段放在區域與頁面之前，因為業務規則常會決定要不要某些頁面（例如非賣品就沒有結帳頁）。
- 「開發說明（設計者補充）」不列入訪談，設計者要求時才寫。
- 首頁新增折疊區塊、完整度表新增列，或燈箱新增頁籤時，同步檢查本表有階段會問到，沒有就補一個階段或併入既有階段。
