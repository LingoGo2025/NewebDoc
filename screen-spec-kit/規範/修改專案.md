# 修改既有專案

本資料夾（`規範/`）是通用的維護流程與設計規範，任何 AI 都依此工作；專案專屬規則寫在專案根目錄的 `專案規則.md` 與 `project.json`，**兩者衝突時以專案為準**。

## 開始前（每次）

1. 找到專案根目錄（有 `project.json`、`scripts/check.py`）。之後的指令都在根目錄執行。
2. 讀 `project.json` 與 `專案規則.md`（專案的區域歸屬、業務規則、品牌素材、配色、目前狀態）。回答語言依專案規定。
3. 依要改的東西，只讀需要的規範（都在本資料夾）：

| 要改的東西 | 讀 |
|---|---|
| 任何修改（必讀） | `workflow.md` |
| 向使用者提問、確認範圍（必讀） | `questioning.md` |
| 開發說明、SA 規格、API 規格，或頁面功能／欄位／文案有變 | `spec-writing.md` |
| 流程（`flows/*.puml`），或頁面增刪、更名、搬移、改功能 | `flows.md` |
| 系統架構、外部系統、業務模組、使用者角色，或頁面增刪 | `architecture.md` |
| index.html 燈箱、首頁折疊區塊、文件完整度 | `index-page.md` |
| 從零建立新專案 | `新專案.md` |
| 新增頁面的 SVG 初稿、品牌配色（`theme`）、各區版型（`mockup`） | `mockup.md` |

## 標準流程（細節見 workflow.md）

1. **查影響範圍**：`python3 scripts/impact.py <頁面ID或關鍵字…>`。
2. **向使用者確認範圍**：回報影響清單，分「確定要改」與「待確認」。**使用者同意前不要改檔**。需求不明確、與規則衝突或碰到待確認項目時先問，不自行補規格。提問依 `questioning.md`：先查再問、選擇題優先（第一個為建議答案）、一次一個主題、敏感領域不給建議答案、答不出來就標待確認並繼續。
3. **只讀需要的段落**：`python3 scripts/section.py <ID|flow-key|章節關鍵字…>`；SVG 用 grep 定位。
4. **先改 Markdown，再局部改 SVG／流程／index.html**；頁面功能、欄位、狀態、文案有變時，同步改該頁「開發說明（AI 補充）」。
5. **記錄**：在對應 Markdown 的「## 更新紀錄」最上方加一行（日期：說明改了什麼、已核對的流程與頁面、哪些沒改）。
6. **同步與檢查**：依下表執行，最後 `python3 scripts/check.py`。錯誤須修正，提醒回報使用者。

## 收尾清單

| 這次改了 | 執行 |
|---|---|
| 新增頁面規格段落 | `python3 scripts/page_stub.py <ID> <名稱> --desc "…"` |
| 新增頁面 SVG（初稿） | `python3 scripts/mockup.py <描述.json>`（見 `mockup.md`） |
| 頁面 SVG 文字 | `python3 scripts/sync_screen_text.py <ID…>` |
| 共用選單表，或 `theme` 的 `nav_text`／`nav_active` | `python3 scripts/nav.py` |
| 網站地圖節點、區域設定、SVG 檔名或 `theme` 主色 | `python3 scripts/index_build.py` |
| 流程 PUML | `python3 scripts/flow_sync.py` → `plantuml -tsvg flows/<key>.puml`（本機） |
| 架構圖 PUML | `plantuml -tsvg architecture/<key>.puml`（本機） |
| 任何頁面、流程、架構圖 SVG（含以上三項） | `python3 scripts/svg_bundle.py` |
| 開發說明、SA 規格、API 規格、系統架構章 | `python3 scripts/dev_notes.py` |
| **每次都要**（寫完更新紀錄後） | `python3 scripts/inventory.py` |
| **最後** | `python3 scripts/check.py` |

## 示範專案與 plugin 同步

示範專案（`project.json › kit.engine_source` 為 true）還在調整，plugin 要跟著改。每次修改都判斷屬於哪一類：

| 改了什麼 | 歸屬 | 怎麼帶回 plugin |
|---|---|---|
| 頁面、流程、規格內容、網站地圖 | 專案內容 | 不帶回 |
| 專案專屬規則（區域、業務規則、品牌、配色） | `專案規則.md`、`project.json` | 不帶回 |
| 通用規則（設計規範、寫法、維護流程、提問方式、訪談階段） | 示範專案的 `規範/`（plugin 的 `規範/` 是匯出的複本） | 直接改示範專案的 `規範/`，`check.py` 會提醒，執行 `sync_kit.py .`；不寫進 `專案規則.md` 或 AI 入口檔 |
| 工具 `scripts/`、index.html 內容區以外（樣式、燈箱、版型） | 引擎 | 改完 `check.py` 會提醒，執行 `python3 <kit.path>/tools/sync_kit.py .` |
| 新的專案設定鍵、規格章節、首頁區塊或內容區 | 範本 `template/`（內容區另改 `tools/slots.py`、`build_engine.py` 的骨架） | 改範本後執行 `sync_kit.py .`（含空白專案自我測試） |

- 分不清是通用還是專案專屬時，依 `questioning.md` 的「需求釐清」問使用者（例如「這條規則以後每個案子都適用，還是只有這個案子？」）。
- 一般專案（非示範專案）的 `規範/` 是複本，升級時整份替換，不在那裡改；要改通用規則時到示範專案改，再以 `upgrade_project.py` 帶到其他專案。
- 帶回 plugin 後：plugin 版本加一（`sync_kit.py` 會自動做，只改範本時加 `--bump`），在 plugin `README.md`「更新紀錄」寫一行。
- 回報時說明這次有沒有帶回 plugin、版本是多少。

## 不可做

- 不整份讀取規格 Markdown、`index.html`、SVG 或 `assets/*.js`。
- 不自行補 API、金流、法規、商業政策的未知內容；一律標「待確認」。
- 不在一般專案裡改引擎（`scripts/`、index.html 內容區以外的部分）；引擎只在示範專案改，改完依上方「示範專案與 plugin 同步」帶回 plugin，其他專案用 `upgrade_project.py` 升級。index.html 平常只改內容區 `<!-- [slot:…] -->`。
- 不手改工具產生的內容：index.html 的網站地圖區塊與 `#project-config`、`assets/svg_sources.js`、`dev_notes.js`、`inventory.js`、SVG 的 `<g data-nav>`、PUML 的 `[legend:…]`／`[style:…]` 區塊。
- 不用會把原稿送到線上的渲染方式（如 `render_plantuml.py`）；只用本機 `plantuml`。
- 不產生 PNG 放進專案；預覽圖只放暫存目錄。
- 不填寫、不刪改「開發說明（設計者補充）」，除非設計者明確要求。
- 除非使用者要求，不新增或執行測試（上表的唯讀檢查工具除外）。
- 不重新執行專案標示為「已過時」的產生器（見 `專案規則.md`）。

## 回報

完成後用幾句話說明：改了哪些頁面、流程、圖；`check.py` 的結果（錯誤數、提醒內容）；還有哪些「待確認」需要使用者決定。
